Visprflow Overnight Build

Phases 0 through 3 are built, audited and installed. The app runs, transcribes on-device, and idles at 6 MB. Three permission dialogs are waiting for you, and only you can click them.

Do this first

Four minutes, then it works

  1. Open the app. It is at ~/Applications/Visprflow.app and already running. Its setup window is open behind your other windows; the menu bar icon is a crossed-out microphone until the grants land.
  2. Grant Microphone, Accessibility and Input Monitoring. Each has a Request button. macOS shows those dialogs only to a person at the keyboard, which is the one thing I could not do for you.
  3. Set the fn key to "Do Nothing" in System Settings, Keyboard. macOS opens the emoji picker before any app sees that key. The setup window detects this and links straight to the pane. On an external keyboard, switch the trigger to Right Option instead.
  4. Pick where rewrites go in the setup window. The default costs you nothing: quick cleanup runs on this Mac instantly, and compiled prompts go through your Claude subscription. An API key is offered as the fast option, not a required one.

Then hold fn in any text field and say something. Release. Watch the overlay. In a terminal running Claude Code you get a preview and press ⏎; in Slack the text just appears.

Correction, 8 September 2026: the “6 MB idle memory” claimed here was wrong. It came from ps rss, which counts neither Core ML's weight buffers nor the Neural Engine's allocation, and it was read before any model had loaded. Measured properly with footprint(1), the shipped build was holding 1251 MB, peak 1385 MB. The cause was placing the speech encoder on the GPU, where its weights are Metal buffers in the app's own heap; on the Neural Engine the same model costs 16 MB in-process and transcribes twice as fast. That is now the default, and make verify-memory measures it on every run rather than leaving it to a person with a terminal.

The speech pipeline is verified end to end without a microphone. Audio is synthesised with the built-in say command, run through the same resampling path as live capture, and transcribed by the real model. That gives known ground truth and needs no permission. Three seconds of silence produced no words at all, which is the hallucination failure Whisper is known for.

What I could not verify is anything that needs a permission dialog: holding the key, capturing from the microphone, and pasting into another app. Those paths are built and unit-tested, but the first real end-to-end dictation will be yours.

One measured gap. Transcription ran at 32× real time, not the 190× the vendor benchmarks claim. That is a debug build under a test host with a cold Neural Engine. For a ten-second dictation it means roughly 310 ms rather than the 80 ms the plan budgeted. Still fast enough to feel instant, and worth re-measuring in the release build.

Audits

Two reviews, and the bug that mattered

Each phase was audited by a reviewer with no stake in the code. The second audit found something I would not have caught by testing the happy path, and it was the kind of bug that costs a user real trust.

A failed recompile could disable your keyboard

While a compiled prompt waits for approval, the app captures ⏎, ⇥, esc and R, because the overlay never takes focus and has no other way to hear them. If recompiling failed, say because the network dropped, the overlay disappeared but the capture stayed on. Those four keys, including the plain letter R, would stop working in every app, with nothing on screen to explain why. Pressing Return to recover would paste the previous dictation into whatever window happened to be focused.

Guardrails rejected half of ordinary technical speech

The check that stops the model inventing file names split compound words at their capitals. "GitHub" became "git" and "hub", neither of which you said, so a correct rewrite was thrown away and replaced with the raw unpunctuated transcript. The reviewer measured this at a 50% false-positive rate on words like TypeScript, JavaScript, iPhone and Node.js. It now also accepts an identifier whose compound form appears in what you said.

Probing the workspace could throw the dictation away

Working out which app and project you are in ran inside the keyboard callback, and it shells out to ps, lsof, git and AppleScript. macOS disables a keyboard hook whose callback is slow, and a disabled hook loses the key release, which discards the recording you just made. That work now runs while you are still speaking and is joined only when the transcript is ready.

Seven more findings were fixed the same way: a new dictation now cancels the previous one instead of letting it finish and paste; mid-stream API errors and truncated responses fail rather than being pasted as if complete; Right Option registers its release while the left one is held; a cancelled paste stops spinning; agents installed through npm are recognised by reading the command line rather than the executable name.

Every one of them has a regression test. Two more bugs were caught by tests I wrote before the audits, including one where saying just the word "verbatim" would have inserted nothing at all.

Added after you woke up

Using your subscription instead of an API key

You asked whether the Claude subscription could replace paid API calls. It can, through the claude command line tool in print mode. I measured both on this Mac and built three providers rather than picking one.

ProviderFirst wordCompleteCostHandles
On this MacinstantinstantfreeFillers, stutters, spoken punctuation, capitalisation. No model involved.
Your subscription~3 s6–10 sincluded in your planEverything. Same models, same quality.
API key~0.7 s1–2 s~$0.002 eachEverything, fastest.

The default mixes them, because cleanup and compilation have opposite needs. Tidying "hey can you send me the figma link" happens constantly and has to feel instant, and it is mechanical enough to do with rules. Restructuring a rambling request into a prompt happens rarely, is worth waiting for, and you are watching a preview while it works. So quick cleanup runs locally and compiled prompts go to your subscription. Nothing costs extra.

Local cleanup deliberately refuses one thing. Resolving "the call is at nine, no wait, eleven thirty" needs judgement about which half to keep, and getting it wrong silently changes what you meant. Those transcripts are detected and handed to a model automatically.

Verified against the live subscription. The full pipeline was run through the real CLI. The rambling login example came back as: "Users are getting logged out after their token expires. I think the bug is in the token refresh logic under src/auth/ (not the session refresh). Look into that and write a test that reproduces it first, then fix it. Don't touch the session code." The self-correction was applied, the constraint survived, nothing was invented. It also rewrote a question rather than answering it. That took 8.7 seconds.

One bug worth recording: the CLI's --disallowed-tools flag takes a list, so a prompt placed after it is swallowed as another tool name and the tool exits saying it received no input. The prompt has to sit immediately after -p. There is a regression test pinning the argument order.

Honest limits

What is not done, and what I could not check

  • No notarisation. This Mac has no Apple Developer ID, so the app is ad-hoc signed. It runs fine for you, but it cannot be given to anyone else without Gatekeeper complaining, and there is no automatic updating.
  • Permission grants are tied to the exact binary. Launch from ~/Applications. If you rebuild and run from build/, macOS treats it as a different app and asks again. The README explains how a self-signed certificate avoids this during development.
  • No live dictation was ever run. Everything downstream of the microphone is tested; the microphone itself needs a permission I could not grant.
  • The API path has never been exercised for real, since there is no key on this machine. Its request shape is unit-tested against the current model contracts. The subscription path, which is now the default for compiled prompts, has been run end to end against the live model.
  • Selected text, screen OCR and the clipboard are not yet used as context. Repository vocabulary is, which is the piece that fixes mangled technical terms.
  • Latency has not been measured end to end, only per stage. The instrumentation is in place: every dictation writes its per-stage timings to the local database.

The thing to try first. Open a terminal, run Claude Code, hold fn and ramble at it: something with a false start and a self-correction, like the login bug example on the plan page. The preview should come back as a structured request with your correction applied and nothing invented. That single interaction is the whole thesis of the project.
