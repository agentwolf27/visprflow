The finding that changes the plan

We already own a streaming engine

FluidAudio 0.15.6 — already pinned in Package.resolved — ships true cache-aware streaming ASR. Read directly from the checkout in our own build tree, not from docs: StreamingUnifiedAsrManager at 320 ms chunks, StreamingEouAsrManager at 160 ms, and a two-tier volatile/confirmed SlidingWindowAsrManager. No dependency bump, no model swap.

Today the pipeline is strictly serial: DictationController.run() transcribes only after capture.stop(). Every second you spend speaking is idle compute.

Two corrections worth recording before anyone writes code against it: StreamingAsrManager is a protocol, not a class, and the published docs' .ms1600 is really .ms1280 and will not compile.

It also exposes configureVocabularyBoosting, which means the repository vocabulary could bias recognition at the acoustic layer instead of only telling the rewriter how to spell things afterwards. "aut midway" would come back as "auth middleware" rather than being repaired.

Plan

Ordered by what you would feel

Now — a day's work, all low risk

1

Stop clearing the pre-roll ring on engine start

premise was wrong

A one-line bug that defeats the feature built to stop first-word clipping. startEngineIfNeeded calls ring.removeAll(), so a cold start has zero pre-roll and the ring only helps within the 6 s linger window.

Also raise pre-roll from 0.5 s to 1.0 s. That is 64 KB of memory.

Sfirst-word clipping

Checked before changing it, and the recommendation was wrong. startEngineIfNeeded returns early when the engine is already running, so removeAll() fires only on a cold start — where everything in the ring predates the dictation by minutes. Deleting it would have spliced stale audio onto the front of what you just said. The line stayed; only the pre-roll went to 1.0 s.

2

Post-roll tail after key-up

shipped

Tap buffers lag the wall clock by a buffer period, so capture.stop() truncates the last word. Superwhisper shipped exactly this fix: "delay before stopping recording to avoid losing last word".

Make stop() async and await ~120 ms of further tap delivery before snapshotting.

Strailing-word loss
3

Warm-up inference and GPU encoder placement

half of it reverted

warmUp() loads the model but never runs one, so the first dictation after launch pays Core ML compilation and ANE scheduling. Transcribe 0.3 s of silence and throw it away.

Separately, encoderComputeUnits: .cpuAndGPU is ~8% faster and WER-neutral per FluidAudio's own benchmark. One argument.

Sfirst-run spike

The warm-up was right; the GPU placement was not. Running one throwaway inference at launch stayed and did its job. Moving the conformer encoder to the GPU cost 1222 MB of our own heap and made transcription slower — 306 ms against the Neural Engine's 143 ms. Reverted, with a test, so that trade is never made on a vendor benchmark again.

4

Trap the uncatchable exceptions

shipped

We already lost hours to one of these: AVAudioEngine.prepare() throws NSException, which unwinds past Swift's catch and dies silently. A tiny Objective-C shim with @try/@catch around installTap, prepare and start turns a silent death into a recoverable error.

Ssilent failure
5

Runtime guard against a bad trigger key

shipped

If the trigger fires more than five times in ten seconds with sub-300 ms recordings, say so: "this key looks like it's firing while you type — change it?" This would have caught the Left Shift choice in seconds rather than after a crash.

Swould have caught today's bug

Next — robustness

6

Audio device and wake recovery

shipped

There is no AVAudioEngineConfigurationChange observer and no wake observer anywhere in the project. Connect AirPods mid-session and the level meter reads zero with no error; the format mismatch raises an uncatchable exception. AirPods make this routine because they drop to 16 kHz whenever the mic is active.

Rebuild the engine outright rather than restarting it — a stale HAL device ID survives a restart.

Msilent dead mic
7

Pin the paste target captured at record start

shipped

Non-preview destinations paste into whatever app is focused when the compile lands. Dictate into Slack, switch to Terminal during a 6 s compile, and your message goes into the shell.

Worth doing well: both major open-source apps declined this on scope grounds, and users describe the failure as making the tool "feel fragile". It is the clearest differentiation available.

Mtext in the wrong app
8

shipped

consume() allocates a buffer per callback and appends to a growing array under a lock the main actor contends 30 times a second. Preallocate and reserve capacity, or hand buffers straight to the streaming manager once item 10 lands.

shipped

Then — the rearchitecture that makes it fast

10

Stream transcription while you speak

shipped as a preview only

Add a streaming transcriber behind the existing Transcriber protocol, which already anticipates this. Feed each buffer to appendAudio, wire the partial callback to the overlay, call finish() on key-up.

Text appears while you talk, and key-up to transcript drops to near zero. Show partials in our overlay, never in the target field — retracting text you already inserted is unreliable in exactly the apps that refuse AX insertion.

Lthe big one

Built, then half of it reversed on measurement. The overlay shows words as you speak — 16 partials on one sentence, the tail intact, clean between dictations. But the final transcript stays with the batch model. Streaming heard “first message about the passer” for “parser”, and the batch model does 4.9 s of audio in 143 ms — a fifth of a second, once, at the end. Preferring the streamed text buys a saving nobody can perceive at a cost you can read. For a tool whose whole job is an exact prompt, that trade is backwards.

11

Speculative compile on a stable prefix

withdrawn

Once partials exist, start the rewrite when the transcript stops changing for ~300 ms. On key-up, keep the in-flight result if the final matches, otherwise cancel and restart. This is Alexa's dual-endpointer pattern, and our cancellation plumbing already has the right shape.

Hides most of the rewrite latency behind you still talking. Gate it to the API provider so a mismatch wastes tokens rather than seconds.

Mhides the rewrite

Lost its premise with item 10. Speculation pays only if the text it speculated on is the text that gets used. Against a batch transcript that differs from the stream, most of the work is thrown away — and the failure mode is not a wasted call, it is a confidently wrong prompt handed to an agent.

12

Vocabulary boosting at the acoustic layer

not buildable as written

Feed the repository vocabulary to configureVocabularyBoosting so technical terms are recognised correctly rather than repaired afterwards.

Mtechnical accuracy

The method is real; it is not on our engine. configureVocabularyBoosting exists on UnifiedAsrManager, SlidingWindowAsrManager and the streaming managers — but not on AsrManager, the batch engine that produces the transcript. Having it means replacing the batch engine outright: a different change with its own accuracy question, not an addition to this one.

Measured after shipping · 8 September 2026

The app was idling at 1.2 GB, and item 3 was why

Measured on the installed release build, running for five days: phys_footprint 1251 MB, peak 1385 MB. The original plan budgeted “50 to 150 MB idle”, listed Wispr Flow's “~800 MB idle” as a reason to build this at all, and named our advantage in the very same row: “model unloads after idle”. We were half a gigabyte heavier than the thing we set out to replace.

The obvious suspect was item 10 — a second Parakeet, held for the live preview. That was wrong, and the heap said so: 1.21 GB sat in MPSNDArray and Core ML MIL allocations. Metal, not the Neural Engine. The streaming model runs on the ANE and shows up in a separate region entirely.

So it was item 3 — “placing the conformer encoder on the GPU is roughly 8% faster end to end”, taken from the vendor's benchmark and never checked here. GPU weights are Metal buffers in our own heap; Neural Engine weights are not. Measured both ways on this machine, best of three transcriptions of 4.9 s of speech:

Encoder placementIn-process memoryTranscription
.cpuAndGPU — what we shipped1222 MB306 ms
.cpuAndNeuralEngine — now the default13 MB143 ms

The Neural Engine is ninety-four times lighter and twice as fast. The 8% went the other way on this hardware. The encoder moved back, and make verify-memory now measures what we actually ship, with a ceiling that fails the build if the batch model creeps past 300 MB of our own heap. The comparison is still one command away — VISPRFLOW_ENCODER=gpu make verify-memory — so nobody has to take this on faith.

Confirmed on the rebuilt app, not just in a test: phys_footprint 40 MB, peak 74 MB, with MALLOC_MEDIUM down from 1161 MB to 11 MB. The model's weights now sit in the Neural Engine's own region where they belong. That is inside the 50–150 MB the plan budgeted, and a thirty-first of what the app was holding this morning.

Separately, the streaming model from item 10 is now released after ten minutes without a dictation, which returns its share of the Neural Engine's allocation. Reloading is automatic, and every failure path in that code already falls through to the batch transcript, so the worst case is a dictation without a live preview — never a lost prompt.

The build report's “6 MB idle memory” was wrong, and has been corrected. It came from ps rss, which counts neither Core ML's weight buffers nor the Neural Engine's allocation, and it was read before any model had loaded. The right tool is footprint(1); the right moment is after a dictation. That is how a headline number ends up off by a factor of two hundred — and why the memory figures on this page are produced by a test, not by a person with a terminal.

Second audit sweep · 8 September 2026

Ten more, found and fixed

None of these were on the original twelve. They came out of reading the code the twelve produced.

DefectWhat it would do to you
The overlay held the controllerController owns the panel, panel's hosting view owns the root view, root view held the controller. Nothing was ever released — audio engine and event tap included.
Both timers slept during trackingTimer.scheduledTimer runs in default mode only. Open a menu and the level meter freezes — and so do the silence detector and the five-minute hold ceiling, the two things that end a dictation nobody is watching.
The event-tap watchdog tooSame cause, worse timing: a busy main thread is exactly when macOS disables the tap, and exactly when a default-mode watchdog is asleep.
The tap port was never invalidatedDisabling stops events; only CFMachPortInvalidate tears the port down. Every trigger change leaked another Mach port for the life of the process.
Cycling the level ran out the clockThe 90 s preview deadline was armed once and never renewed, so a few level changes made a prompt vanish mid-decision.
The preview checked focus too earlyPressing Return checked the frontmost app, then pasted seconds later without looking again — and a prompt abandoned that way left no trace in history. The check now runs immediately before the paste, and records what happened. Insertion itself is left uncancellable on purpose: it sleeps between chunks, so cancelling it mid-flight would leave half a prompt in the editor.

Decided against

Two things not to build

Raw-first insertion. Inserting the verbatim transcript then replacing it with the polished version only works where the field can be read back and verified through the accessibility API — which fails in terminals, Electron apps and web views, the exact places we care about. Synthesized backspaces race with your own typing. The preview flow already solves this honestly.

Tuning the clipboard restore delay. The definitive analysis in Handy's tracker puts it plainly: "any fixed delay has a lag that beats it." Our inserter already verifies with a read receipt before restoring, which is the correct design and better than most shipping competitors. Leave it alone.

Reference

Trigger keys, settled

Recommended default is hold Right Option, double-tap to lock. It is a modifier, so it keeps firing under Secure Event Input where letters and Space die; it types nothing; and it leaves Left Option free for accented characters.

RefuseReason
Shift (either)Types every capital; five presses toggle Sticky Keys
Caps LockA toggle, not a hold; often already remapped
Letters, digits, Space, Return, Tab, DeleteDestroys typing, and blocked under Secure Input
Left CommandThe primary shortcut modifier for every app
F11Show Desktop; macOS reserves it even when disabled
EscapeAlready cancels a dictation

Warn but allow: Left Option (five presses toggle Mouse Keys), Control (collides with macOS Dictation's double-tap), fn (the Globe setting and Sequoia's Globe layer). Timing constants worth matching: 400 ms double-tap window, 300 ms minimum press, 5 minute safety ceiling — all three now match the code.
